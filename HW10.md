### What is AOP?

AOP stands for **Aspect Oriented Programming**. 

In a typical application, certain behaviours such as logging, security, and transaction management are needed across many different parts of the code, such as in different Service class. 

Instead of writing the same logic repeatedly in every class, AOP allows you to separate these **cross-cutting concerns** into a single dedicated place called an **Aspect**. 

The Aspect contains the logic I want to apply. I tell Spring **where** and **when** to apply it using @PointCut, @Before, or @After. For example, before a method runs, after it returns, or when an exception is thrown. 

Spring then automatically weaves this logic into your application at the specified points without you touching the original classes. 

### **What is JoinPoint and Aspect in AOP?**

**Join Points decide where:** 

A JoinPoint is a specific point during the program execution, where an Aspect can be applied. 

In Spring AOP, a JoinPoint is typically a method execution — it represents the method that is currently being intercepted.

It also carries useful information about the method being executed, such as the method name, arguments passed in, and the target object.

An Aspect is a class that contains cross-cutting logic — the shared behaviour you want to apply across your application, such as logging, security, or transaction management. Instead of writing this logic in every class, you write it once in an Aspect and tell Spring where to apply it.

### **What are Aspect, JoinPoint, Pointcut, Advice, and Target?**

**Aspect**

An Aspect is a class that contains cross-cutting logic that you want to apply across your application, such as logging, security, or transaction management. 

The Aspect determines the AOP class.

Instead of writing this logic in every class, you write it once in an Aspect and Spring applies it automatically where needed.

**JoinPoint**

A JoinPoint is a specific point during the execution of your program where an Aspect can be applied. In Spring AOP it is typically a method execution. It also carries information about the method being executed, such as the method name and the arguments passed in.

**Pointcut**

A Pointcut is an expression that defines exactly which methods the Aspect should apply to. It decides where to apply and usually combined with a package path. 

While a JoinPoint is a single method execution that is happening right now, a Pointcut is the rule that selects which JoinPoints to intercept. 

JoinPoint is where it is happening. Pointcut is the rule for selecting where to apply.

**Advice**

Advice is the actual action that runs when a Pointcut is matched. 

It defines when the logic should run relative to the method — before it executes, after it returns, or when it throws an exception.

Types of Advice:

- Before — runs before the method
- After Returning — runs after the method returns successfully
- After Throwing — runs if the method throws an exception
- Around — wraps the method completely

**Target**

The Target is the original object whose method is being intercepted by the Aspect. It is the class that contains your business logic — it has no knowledge that an Aspect is being applied to it.

### ApplicationContext vs. BeanFactory

**BeanFactory**

BeanFactory is the most basic container in Spring. 

It only creates and manages beans. It uses lazy loading: it only creates a bean when you actually ask for it.

**ApplicationContext**

ApplicationContext is built on top of BeanFactory. It does everything BeanFactory does but adds more features on top. It uses eager loading: it creates all singleton beans at startup, not when you ask for them.

Extra features ApplicationContext provides:

- Reads messages from properties files
- Publishes events to beans that are listening
- Integrates with Spring AOP automatically
- Supports annotations like @Component, @Autowired

### How does Spring MVC Working Flow?

When a client sends an HTTP request, it first hits the DispatcherServlet, which acts as the front controller and receives all incoming requests. The DispatcherServlet then consults the HandlerMapping to figure out which Controller should handle the request based on the URL. Once the correct Controller is found, the DispatcherServlet calls it, and the Controller processes the request — executing the business logic, interacting with services and repositories if needed — and then returns a ModelAndView object, which contains the data and the name of the view to display. The DispatcherServlet then passes this to the ViewResolver, which maps the view name to an actual view template such as an HTML file. Finally the view is rendered with the data from the Model and the response is sent back to the client.

### How does @Autowired work?

When Spring starts up, it scans all classes marked with @Component, @Service, @Repository, or @Controller and registers them as beans in the ApplicationContext.

When Spring encounters @Autowired on a constructor, field, or setter, it looks inside the ApplicationContext for a bean that matches the required type and injects it automatically.

**Step by step**

1. Spring starts and scans all classes
2. It finds @Component classes and creates beans for them
3. It sees @Autowired on a field or constructor
4. It looks in the ApplicationContext for a bean of that type
5. It finds the matching bean and injects it
6. If no matching bean is found — Spring throws an error at startup

### **@Autowired and @Qualifier**

**@Autowired is an annotation provided by Spring that enables automatic dependency injection.** 

When Spring starts up, it scans all the beans registered in the ApplicationContext, and whenever it encounters @Autowired on a field, constructor, or setter, it automatically finds a bean of the matching type and injects it. 

This removes the need to manually instantiate objects, keeping the code clean and loosely coupled.

However, a problem arises when there are multiple beans of the same type registered in the container. For example, if two classes both implement the same interface, Spring gets confused about which one to inject and throws a NoUniqueBeanDefinitionException at startup.

This is where @Qualifier comes in. **@Qualifier is used alongside @Autowired to specify exactly which bean should be injected by providing the bean name.** This resolves the ambiguity and tells Spring precisely which implementation to use.

In my project, I use @Autowired to inject dependencies such as my EmployeeRepository into my EmployeeService, so that Spring manages the wiring between layers automatically without me having to create objects manually. If I have multiple implementations of the same interface, for example, I have EmployeeRepository impl1, I would use @Qualifier to specify which one I want injected.

### **2 Use Cases for @PostConstruct and @PreDestroy**

**@PostConstruct**

This method runs after dependency injection is completed.

Use cases:

- Load configuration or cache data into memory.
- Initialize resources such as API clients or database connections.

**@PreDestroy**

This method runs before the bean is destroyed.

Use cases:

- Close database connections or thread pools.
- Release resources before application shutdown.
