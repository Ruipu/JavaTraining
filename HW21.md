### **Encryption vs Hashing vs Encoding**

**Encryption is used to protect sensitive data. It changes readable data into unreadable ciphertext.** 

The process is reversible, but only someone with the correct key can decrypt the data. Encryption is commonly used for database fields, files, and network communication.

Hashing is different because it is designed to be one-way. 

**It converts input data into a fixed-length hash value. The original value should not be recoverable from the hash. Hashing is often used for password storage and data integrity checks.**

**Encoding only changes the format of data so that another system can store or transmit it correctly. It does not provide security because it can be easily reversed. Base64 is a common example of encoding.**

### **Authentication vs Authorization**

**Authentication verifies the identity of a user or service. It answers the question,** **“Who are you?”** A system may use a password, verification code, fingerprint, or security token to authenticate a user.

**Authorization decides** **what an authenticated user is allowed to do.** It answers the question, “What can you access?” For example, both an employee and an administrator can log in, but only the administrator may delete records.

Authentication normally happens first. After the system knows the user’s identity, it checks the user’s roles and permissions.

### **HTTPS, Certificates, and Key Rotation**

HTTPS is the secure version of HTTP. 

**It uses TLS to encrypt data sent between a client and a server.** This prevents attackers from easily reading or changing passwords, tokens, and other sensitive information during transmission.

**A digital certificate helps the client verify the identity of the server.** 

The certificate includes information such as the domain name, public key, expiration date, and certificate issuer. Browsers check this information before trusting the connection.

**Key rotation means replacing old cryptographic keys with new ones.** 

Keys should not be used forever because they may be leaked or exposed. Regular rotation reduces the damage caused by a compromised key.

### **JWT Token Structure**

**A JWT contains three parts: the header, payload, and signature.**

**The header describes the token type and the signing algorithm.** 

The payload contains claims such as the user ID, username, role, issuer, and expiration time.

**The signature is used to verify that the token has not been changed.** The server creates it with a secret key or private key. When the token is received, the server verifies the signature before trusting the payload.

**The header and payload are encoded, not encrypted.** Anyone who has the token can usually read them. Sensitive information such as passwords should never be stored in a normal JWT payload.

### **OAuth 2.0 and OIDC**

**OAuth 2.0 is an authorization framework. It allows one application to access resources from another service without receiving the user’s password.**

For example, an application may receive an access token that allows it to read a user’s profile. The token usually contains limited permissions called scopes. The application sends the access token when calling the protected API.

**OIDC, or OpenID Connect, is built on top of OAuth 2.0. It adds authentication. OIDC provides an ID token that contains information about the logged-in user.**

The access token is mainly used to access APIs. The ID token is mainly used to identify the user.

### **LDAP**

**LDAP stands for Lightweight Directory Access Protocol. It is used to access information stored in a directory service.**

Many companies use LDAP directories to store user accounts, groups, departments, email addresses, and other organizational information. An application can connect to LDAP to verify a user’s credentials.

LDAP can also be used for authorization. For example, an application may check whether a user belongs to an administrator group. Microsoft Active Directory supports LDAP, although Active Directory provides many other identity-management features as well.

### **SQL Injection and Prepared Statements**

**SQL injection happens when untrusted user input changes the structure of a SQL query. It usually happens when an application directly joins user input with SQL text.**

An attacker may enter SQL commands instead of normal data. This may allow the attacker to bypass login checks, read private information, modify records, or delete data.

**Prepared statements prevent this problem by separating the SQL command from the user input. The SQL structure is created first, and the user values are passed as parameters.**

The database treats these parameters as data instead of executable SQL. This is safer than manually combining strings or escaping special characters.
