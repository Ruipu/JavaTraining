### What is Index

An index is a special data structure in a database that allows the database to find data quickly without scanning the entire table. Index is like the contents in a book; I don't need to read every page, you just look up the topic and jump straight to the right page.

### Clustered Index vs Nonclustered Index

**A clustered index** determines the physical order of data stored on disk. A table can only have one clustered index, and the primary key is one by default. 

**A nonclustered index** is a separate structure that stores the index value and a pointer to the actual data row. 

***A table can have multiple nonclustered indexes.*** 

In short, a clustered index is the data itself sorted in a certain way, while a nonclustered index is an extra "lookup table" built on the side.

### Data Structure for Index

Most databases use a B-Tree (Balanced Tree) as the underlying data structure for indexes. 

B-Tree keeps data sorted and allows searches, inserts, and deletes in O(log n) time. 

Some databases also use Hash indexes, which are faster for exact-match lookups but cannot handle range queries like greater than or less than. 

PostgreSQL also supports GIN and GiST indexes for full-text search and geometric data.

### View vs Stored Procedure

A view is a saved SQL query that acts like a virtual table. You query it just like a regular table, but it does not store data itself. A stored procedure is a saved block of SQL code that can contain logic, loops, and conditionals. You call it like a function and it can accept parameters, return results, and perform multiple operations at once. A view is for simplifying data retrieval, while a stored procedure is for encapsulating business logic.

**A view is a saved SQL query that behaves like a virtual table. It stores no data — every time you query it, the database runs the original SQL behind the scenes and returns fresh results. It is best used to simplify complex queries you run often.**

```sql
CREATE VIEW dept_avg_salary AS
SELECT d.name, AVG(e.salary) AS avg_salary
FROM Employee e
JOIN Department d ON e.dept = d.key
GROUP BY d.key, d.name;

-- Using View.
SELECT * FROM dept_avg_salary;
```

**A stored procedure is a saved block of code that lives inside the database. Unlike a view, it can accept parameters, contain logic, and perform insert, update, or delete operations. You call it like a function. It is best used to encapsulate business logic that involves multiple steps.**

```sql
CREATE PROCEDURE give_raise(dept_id INT, raise_amount NUMERIC)
LANGUAGE plpgsql AS $$
BEGIN
    UPDATE Employee
    SET salary = salary + raise_amount
    WHERE dept = dept_id;
END;
$$;

CALL give_raise(1, 5000);
```

### View vs Materialized View

A regular view is just a saved query — every time you query it, the database runs the underlying SQL fresh and returns the latest data. A materialized view actually stores the query result on disk like a real table. This makes reads much faster, but the data can become stale and needs to be refreshed periodically. Use a regular view when you always need up-to-date data, and use a materialized view when you need better read performance and can tolerate slightly outdated data.

**A materialized view is like a regular view, but it actually saves the query result to disk. This makes reads much faster because the database does not re-run the SQL every time. The downside is the data can go stale, so you need to refresh it manually or on a schedule.**

```sql
CREATE MATERIALIZED VIEW dept_avg_mat AS
SELECT d.name, AVG(e.salary) AS avg_salary
FROM Employee e
JOIN Department d ON e.dept = d.key
GROUP BY d.key, d.name;

REFRESH MATERIALIZED VIEW dept_avg_mat;
```

### How to Tune a SQL Query

- First, use EXPLAIN or EXPLAIN ANALYZE to see how the database is executing your query and identify slow steps.
- Add indexes on columns you frequently use in WHERE, JOIN, or ORDER BY clauses.
- Avoid using SELECT star and only fetch the columns you actually need.
- Avoid functions on indexed columns in WHERE clauses because they prevent the index from being used.
- Break complex queries into smaller pieces using CTEs to make them easier to optimize.
- Also make sure statistics are up to date so the query planner makes good decisions.

### Saga vs 2PC

Both Saga and 2PC (Two-Phase Commit) are patterns for managing transactions across multiple services or databases. 

**2PC is a synchronous protocol** where a coordinator asks all participants to prepare, then tells them all to commit or rollback together. 

It guarantees strong consistency but is slow and can get stuck if the coordinator fails. 

Saga breaks a large transaction into a sequence of smaller local transactions, each with a compensating transaction to undo it if something goes wrong. 

**Saga is asynchronous** and more resilient, but only provides eventual consistency rather than immediate consistency. 

2PC is used when you need strict guarantees, while Saga is preferred in modern microservices architectures where availability and scalability matter more.

### Find the average salary per department, only for employees older than30, ordered by average salary descending order.  -> EXPLINA execution plan

```sql
SELECT
    d.name AS department,
    AVG(e.salary) AS avg_salary
FROM Employee e
         JOIN Department d ON e.dept = d.Key
WHERE e.age > 30
GROUP BY d.Key, d.name
ORDER BY avg_salary DESC;

explain SELECT
            d.name AS department,
            AVG(e.salary) AS avg_salary
        FROM Employee e
                 JOIN Department d ON e.dept = d.Key
        WHERE e.age > 30
        GROUP BY d.Key, d.name
        ORDER BY avg_salary DESC;
```

**Explain:**

First, it does a Seq Scan on the Department table, meaning it reads every row from top to bottom. It then takes all that department data and builds a Hash Table in memory, ready for the Join later.

Second, it does a Seq Scan on the Employee table, again reading every single row. While scanning, it applies the Filter age > 30 and throws away anyone who does not meet the condition, keeping only the qualifying employees.

Third, it takes the filtered Employee rows and joins them against the Department Hash Table built in step one. The join condition is e.dept = d.key, so each employee gets matched with their department. This is called a Hash Join.

Fourth, it groups the joined results by d.key and calculates AVG(salary) for each group. This step is called HashAggregate.

Fifth and finally, it sorts the grouped results by avg(e.salary) in descending order and returns the output to you.

The most important thing to notice here is that both tables are using Seq Scan. This means no indexes are being used at all. The database is reading every single row in both tables before doing anything else. For your small dataset this is fine, but on a large table with millions of rows this would be very slow. Adding an index on employee.age and employee.dept would help significantly.
