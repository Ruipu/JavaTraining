### **Point-to-Point Model vs. Publish-Subscribe Model**

**The point-to-point model uses a queue between producers and consumers.** 

A producer sends a message to the queue, and one consumer processes that message. When multiple consumers listen to the same queue, they normally compete for messages. Each message is delivered to only one consumer, so the workload can be distributed among multiple workers.

For example, an order service may place payment tasks into a queue. Several payment workers can consume from that queue, but each payment task should be processed by only one worker. This model is commonly used for background jobs, task distribution, request buffering, and asynchronous processing.

**The main advantage of the point-to-point model is simple workload distribution.** 

Consumers can be added to increase processing capacity, and producers do not need to know which consumer will handle a message. It also provides natural load balancing because messages are divided among available consumers.

**The disadvantage is that one message normally represents one unit of work for one consumer.** 

If several independent systems must receive the same event, one shared queue is not enough. Separate queues or additional routing logic are required. The model is therefore less suitable for broadcasting the same event to many independent applications.

**The publish-subscribe model uses a topic or an exchange instead of a single work queue. A producer publishes an event without directly identifying the consumers. Multiple subscribers can receive and process the same event independently.**

For example, after an order is created, the order service may publish an `OrderCreated` event. The inventory service can reduce inventory, the notification service can send an email, the analytics service can update a dashboard, and the fraud service can analyze the order. Each subscriber receives its own logical copy of the event.

The main advantage of publish-subscribe is extensibility. A new subscriber can be added without changing the producer. It also creates loose coupling because the producer does not need to know how many consumers exist or what they do.

The disadvantage is greater operational complexity. Each subscriber may process events at a different speed, fail independently, or require its own retry strategy. The system must handle duplicate delivery, message ordering, subscriber failures, monitoring, and schema compatibility.

**Kafka can support both patterns through consumer groups.** 

Consumers in the same consumer group compete for partitions, which behaves like point-to-point processing. 

Different consumer groups can read the same topic independently, which behaves like publish-subscribe. Within one consumer group, each partition is assigned to only one consumer at a time.

**RabbitMQ also supports both patterns. A work queue distributes tasks among workers, while exchanges can route one published message to multiple queues for publish-subscribe delivery.**

### **Why Do We Need a Messaging System?**

**A messaging system allows different services to communicate asynchronously.** 

Without messaging, one service usually calls another service directly through HTTP or RPC and waits for the response. **This creates temporal coupling** because both services must be available at the same time.

With a messaging system, the producer can send a message and continue its work. The broker stores the message **until a consumer is ready to process it.** This improves availability because a temporary consumer failure does not immediately cause the producer’s request to fail.

**Messaging systems also provide service decoupling.** 

The producer only needs to know the message destination and message contract. It does not need to know the consumer’s location, implementation language, deployment schedule, or internal business logic.

**Another important reason is traffic buffering.** 

Suppose an application normally receives 1,000 requests per second but suddenly receives 10,000 requests per second. Sending every request directly to a downstream service may overload that service. A message queue can absorb the temporary traffic spike while consumers process messages at a sustainable rate.

**Messaging also supports horizontal scaling.** 

When the workload increases, more consumer instances can be added. In a queue-based system, the additional consumers share the workload. In Kafka, consumer instances in the same group can process different partitions in parallel.

**Messaging systems also improve failure recovery.** 

Messages can remain available after a consumer crashes. The consumer can restart and continue processing. Depending on the technology and configuration, the system may support acknowledgments, retries, dead-letter queues, replication, offset tracking, or event replay.

**Another common use case is event-driven architecture.** 

**Instead of one service controlling an entire business workflow through direct calls, services publish events describing what happened. Other services react to those events independently.** This reduces direct dependencies and makes the architecture easier to extend.

**However, messaging introduces new challenges.** 

**The application must handle eventual consistency, duplicate messages, delayed processing, message ordering, retry behavior, poison messages, schema evolution, and monitoring.** 

A messaging system improves decoupling, but it does not automatically make a distributed system simple.

### **Kafka Architecture**

**Kafka is a distributed event-streaming platform. The main components are producers, consumers, topics, partitions, brokers, replicas, consumer groups, offsets, and the Kafka controller.**

A producer sends records to a Kafka topic. 

A topic is a logical category of events, such as `orders`, `payments`, or `user-activity`. 

A topic is divided into partitions, and each record is appended to one partition. 

Partitions allow Kafka to distribute data across brokers and process records in parallel.

**Each partition is an ordered, append-only log.** 

Every record receives an offset, which identifies its position inside that partition. 

Kafka guarantees record ordering within one partition, but it does not provide one global order across all partitions of a topic.

**Producers can control partition selection.** 

When a record has a key, Kafka normally hashes the key to select a partition. 

Records with the same key are therefore normally sent to the same partition, which preserves their relative order. 

For example, all events for the same customer ID can be sent to the same partition.

**Kafka brokers are servers that store topic partitions and handle producer and consumer requests.** 

A Kafka cluster contains multiple brokers. Partitions are distributed among those brokers so that storage and network traffic can be shared across the cluster.

**For fault tolerance, a partition can have multiple replicas.** 

One replica is the leader, and the others are followers. Producers and consumers communicate with the leader. Followers copy records from the leader. If the leader broker fails, an eligible replica can become the new leader.

**The replication factor determines how many copies of each partition exist.** 

For example, a replication factor of three means that Kafka maintains three copies of the partition on different brokers. Replication improves availability, but it also increases storage and network requirements.

**Consumers read records from topic partitions.** 

Consumers are organized into consumer groups. Within one consumer group, each partition is processed by only one consumer at a time. This allows the group to divide the topic’s workload among its members. Different consumer groups maintain independent positions and can process the same topic for different purposes.

**Kafka tracks a consumer group’s position using offsets.** 

After processing records, a consumer commits offsets. If the consumer restarts, it can continue from the committed position. The timing of offset commits affects delivery behavior. Committing before processing can cause message loss from the application’s perspective, while committing after processing may cause duplicate processing after a failure.

**When consumers join or leave a group, Kafka may perform a rebalance.** 

During a rebalance, partitions are reassigned among the active consumers. Rebalancing allows the group to adapt to scaling and failures, but frequent rebalances can temporarily interrupt processing.

Modern Kafka clusters use the KRaft architecture for metadata management and controller elections. 

The controller manages cluster metadata, broker registration, partition leadership, and other administrative operations. 

Older Kafka deployments used ZooKeeper for cluster coordination, but current Kafka architecture has moved metadata management into Kafka itself.

### **Messages Are Accumulating in Kafka and Consumers Cannot Keep Up. What Should You Do?**

**The first step is to confirm that the problem is consumer lag.** 

Consumer lag is the difference between the latest offset in a partition and the consumer group’s committed or processed offset. Large or continuously increasing lag means that records are arriving faster than the consumer group can process them.

**Next, determine whether the lag affects every partition or only certain partitions.** 

If one partition has much more lag than the others, the topic may have a data-skew problem. This often happens when many records use the same key and are therefore sent to one hot partition.

**The most common solution is to increase the number of consumer instances.** 

Consumers in the same group can process different partitions in parallel. However, the useful number of consumers cannot exceed the number of partitions. If a topic has eight partitions, no more than eight consumers in one group can actively process partitions at the same time. Additional consumers will remain idle.

**If all partitions already have active consumers, consider increasing the number of partitions.** 

This can create more parallelism, but it must be done carefully. 

Increasing partitions can change key-to-partition mappings, affect ordering assumptions, increase broker overhead, and trigger consumer rebalancing. Existing records are not automatically redistributed into the new partitions.

**The consumer application should also be optimized.** 

Check database queries, external API calls, serialization, deserialization, logging, thread usage, batch size, and transaction boundaries. In many systems, Kafka itself is not the bottleneck. The bottleneck is a slow database, a remote service, or expensive business logic inside the consumer.

**Batch processing can improve throughput.** 

Instead of processing and committing one record at a time, the consumer can poll multiple records, process them as a batch, and commit offsets less frequently. This reduces network calls and commit overhead. However, larger batches can increase processing latency and make failure recovery more complicated.

**You should also examine Kafka consumer settings.** 

The poll size, fetch size, maximum processing interval, heartbeat interval, and session timeout must match the application’s processing behavior.

For example, if processing one batch takes longer than the configured maximum poll interval, Kafka may consider the consumer unhealthy and trigger repeated rebalances.

**If the workload involves independent tasks, processing can sometimes be parallelized inside the consumer.** 

However, this must be designed carefully because Kafka consumers are not generally intended to be accessed concurrently by multiple threads. The application must also preserve ordering when ordering is required and commit offsets only after the correct records have finished processing.

**Check whether the consumer is repeatedly failing on the same poison message.** 

A malformed or permanently invalid record may block progress if the application continuously retries it. A retry topic or dead-letter topic can isolate such records so that valid records can continue to be processed.

**Infrastructure resources should also be checked.** 

Consumer CPU, memory, garbage collection, network bandwidth, database connection pools, and container limits may restrict processing capacity. Scaling the number of consumers will not solve the problem if all consumers share the same overloaded database or external dependency.

**If lag is temporary and retention is long enough, the consumer may eventually catch up.** 

If lag grows continuously, the system has a capacity problem. The long-term processing rate must be greater than the long-term production rate. Otherwise, the backlog will continue to increase regardless of short-term tuning.

**Finally, configure monitoring and alerting for consumer lag, processing latency, error rates, rebalance frequency, broker disk usage, and partition skew.** 

The objective is not merely to remove the current backlog, but to identify why processing capacity became lower than incoming traffic.

### **How Does Kafka Deal with Expired Data?**

**Kafka does not normally delete a record immediately after a consumer reads it.** 

Message retention is independent of consumption. 

**A record can remain in Kafka even after every consumer has processed it, and multiple consumer groups can read the same record independently.**

**Kafka stores partition data in log segment files.** 

Retention cleanup normally operates at the segment level rather than deleting individual records immediately. When a closed segment becomes eligible for deletion, Kafka removes the segment according to the topic’s cleanup and retention configuration.

**With the `delete` cleanup policy, Kafka deletes old log segments after they exceed a configured retention time or when the partition exceeds a configured size limit. The default cleanup policy is deletion.**

**Time-based retention controls how long records are kept.** 

For example, a topic may retain records for seven days. After records become older than the retention period, the corresponding eligible log segments can be removed.

**Size-based retention controls how much data each partition may retain.** 

When a partition grows beyond the configured size, Kafka removes older segments to free storage. Because the limit is applied per partition, the approximate topic-level retained size depends on the number of partitions.

**Retention is not an exact expiration timer for each individual message. A record may remain slightly longer than the configured retention period because Kafka deletes complete log segments during periodic cleanup operations.**

**Kafka also supports log compaction.** 

With the `compact` cleanup policy, Kafka attempts to retain at least the most recent value for each message key. Older values for the same key may be removed. This is useful for maintaining the latest state of entities such as customer profiles, account configurations, or product information.

**A compacted topic may also contain tombstone records, which are records with a key and a null value.** 

A tombstone represents deletion of that key. Kafka retains the tombstone for a configured period so consumers can observe the deletion before Kafka eventually removes it.

**A topic can use both `delete` and `compact`. In that case, Kafka compacts older values by key while also removing data according to time or size retention limits.**

**If a consumer remains inactive longer than the available data retention period, the records it has not processed may already have been deleted.** 

Its stored offset may then point to data that no longer exists. 

The consumer must follow its offset-reset configuration, such as starting from the earliest available offset or the latest offset.

### **What Data Volume Can Kafka Handle?**

Kafka does not have one universal maximum data volume. Its capacity depends on the number of brokers, number of disks, disk throughput, network bandwidth, partition count, replication factor, record size, producer rate, consumer rate, compression, retention period, and workload pattern.

Kafka is designed for high-throughput workloads because records are appended sequentially to partition logs, producers can batch records, consumers can fetch data in batches, and partitions can be distributed across many brokers. Topics can therefore scale horizontally by adding partitions and brokers.

When discussing Kafka capacity, it is useful to separate throughput from retained storage. Throughput measures how much data enters and leaves the cluster per second. Retained storage measures how much data remains on disk over the configured retention period.

For example, suppose producers send 100 MB per second and the data is retained for seven days. Before replication and compression are considered, the approximate retained data is:

100 MB × 60 × 60 × 24 × 7

This is approximately 60.5 TB of logical data. With a replication factor of three, the raw disk requirement may be approximately three times the logical size, although compression and filesystem behavior can change the actual value.

Consumer traffic must also be included. If five independent consumer groups each read the entire topic, the brokers must serve the same logical data multiple times. Therefore, network read throughput can be much higher than producer write throughput.

The practical limit is reached when one or more resources become saturated. Common bottlenecks include broker disk throughput, network bandwidth, page cache efficiency, CPU usage from compression or encryption, excessive partition counts, replication traffic, and slow consumers.

Kafka capacity should therefore be established through load testing. The test should use realistic message sizes, compression, acknowledgment settings, partition counts, replication factor, retention, number of consumer groups, and downstream processing behavior.

### **How Do You Calculate the Number of Kafka Partitions?**

Partition count should be based primarily on required throughput, desired consumer parallelism, ordering requirements, expected growth, and broker capacity.

A common throughput-based estimate compares the required topic throughput with the throughput that one partition can support. The basic calculation is:

Required partitions = maximum of producer throughput requirement divided by per-partition producer throughput, and consumer throughput requirement divided by per-partition consumer throughput.

For example, suppose the system must produce 120 MB per second, and testing shows that one partition can safely accept 15 MB per second. The producer requirement suggests at least eight partitions.

If the consumer group must process 120 MB per second, but one consumer processing one partition can handle only 10 MB per second, the consumer requirement suggests at least twelve partitions. In this case, twelve is the more appropriate starting point because it satisfies both sides.

Consumer parallelism is another important factor. Within one consumer group, one partition can be assigned to only one consumer at a time. Therefore, if the system requires twenty consumers to process data in parallel, the topic needs at least twenty partitions.

Ordering requirements may reduce the available parallelism. Kafka preserves order only within a partition. If all events for one business entity must remain ordered, those events should use the same key and remain in the same partition. If the entire topic requires strict global ordering, it may need only one partition, which significantly limits throughput.

Partition count should also include expected future growth. If the current calculation requires twelve partitions but traffic is expected to double, the team may create additional partitions in advance. This avoids frequent repartitioning later.

However, creating too many partitions also has costs. Every partition requires metadata, file handles, memory, leader management, replication work, recovery time, and consumer coordination. Very large partition counts can increase controller workload, rebalance duration, startup time, and operational complexity.

The replication factor does not directly increase consumer parallelism because consumers read the leader partition under normal operation. However, replication increases broker network traffic and disk usage, so it must be considered when determining whether the brokers can support the selected partition count.

The best method is to benchmark one partition under realistic conditions and then calculate the required count with a safety margin. The final value should satisfy throughput, consumer concurrency, ordering, growth, and operational constraints rather than relying on a fixed rule such as “one partition per broker.”

### **AWS SQS vs. RabbitMQ vs. Kafka**

Amazon SQS is a fully managed queue service. Applications send messages to a queue, and consumers poll the queue to retrieve and process them. AWS manages infrastructure, availability, scaling, and maintenance. SQS is well suited for decoupling AWS services, distributing background tasks, buffering requests, and implementing asynchronous workflows.

The main advantage of SQS is operational simplicity. The team does not manage brokers, clusters, disks, replication, or software upgrades. SQS can scale automatically, integrates closely with AWS services, and supports features such as visibility timeouts, long polling, dead-letter queues, and FIFO queues.

The main limitation is reduced infrastructure control. Applications use AWS-defined APIs and service behavior rather than configuring a general-purpose messaging broker. SQS is also fundamentally queue-oriented. A message is normally processed and deleted rather than retained as a replayable event history.

RabbitMQ is a general-purpose message broker. Producers normally publish messages to exchanges, and exchanges route those messages to queues based on bindings and routing rules. RabbitMQ supports work queues, publish-subscribe, direct routing, topic routing, request-reply patterns, acknowledgments, retries, and dead-lettering.

RabbitMQ is especially useful when the application requires flexible message routing, traditional queue semantics, per-message acknowledgments, low-latency command delivery, or AMQP-based integration. Its exchanges provide more explicit routing options than a basic queue service.

The disadvantage is that RabbitMQ generally requires more operational management unless a managed service is used. The team must consider cluster topology, queue types, replication, storage limits, upgrades, monitoring, connection management, and failure recovery.

Kafka is a distributed event log rather than only a traditional message queue. Producers append events to partitioned topics, and consumers track their own positions using offsets. Records remain available according to retention policies even after they are consumed.

Kafka is most appropriate for high-volume event streaming, data pipelines, change data capture, log aggregation, event sourcing, stream processing, analytics, and situations where multiple consumer groups must independently read or replay the same event history.

Kafka’s major advantages are high throughput, partition-based scaling, durable retention, event replay, and support for multiple independent consumer groups. It is suitable when events represent a long-lived stream of business activity rather than temporary tasks that disappear immediately after processing.

Kafka’s disadvantages include greater architectural and operational complexity. The team must design partitions, keys, replication, retention, consumer groups, offset management, schema evolution, lag monitoring, and failure handling. Kafka may be unnecessary for a small application that only needs a simple background job queue.

The choice depends on the use case. SQS is usually preferred for a simple, fully managed AWS queue. RabbitMQ is preferred for flexible routing and traditional messaging semantics. Kafka is preferred for large-scale event streaming, event retention, replay, and multiple independent consumers.

### **AWS SNS vs. AWS SQS**

Amazon SNS is a publish-subscribe notification service. Producers publish messages to an SNS topic, and SNS delivers each message to the topic’s subscribers. Subscribers can include SQS queues, Lambda functions, HTTP endpoints, email addresses, SMS destinations, and other supported targets.

SNS is push-based. When a message is published, SNS attempts to send it to the configured subscribers. It is useful when one event must be distributed to multiple systems, such as notifying several applications that an order has been created.

Amazon SQS is a queue service. Producers send messages to a queue, and consumers poll the queue. A message remains in the queue until it is successfully processed and deleted or until its retention period expires. SQS is useful when work must be buffered and processed asynchronously by one group of workers.

The main conceptual difference is that SNS distributes notifications, while SQS stores work for later processing. SNS normally delivers one published event to every relevant subscription. SQS normally allows one consumer from a competing group of workers to process each message.

SNS by itself does not provide the same queue-based buffering behavior as SQS. If a subscriber is temporarily unavailable, delivery behavior depends on the subscription type and retry policy. SQS provides durable buffering so the consumer can process the message later.

SNS and SQS are commonly used together. An application publishes an event to an SNS topic. Several SQS queues subscribe to that topic. SNS sends a copy of the event to each subscribed queue, and each application processes messages from its own queue independently.

For example, an `OrderCreated` SNS topic may have three subscribed SQS queues. One queue belongs to the inventory service, one belongs to the notification service, and one belongs to the analytics service. Every service receives the event, but each service can process it at its own speed.

This combination provides both fan-out and durability. SNS handles one-to-many event distribution, while SQS buffers messages, supports independent scaling, and protects each consumer from temporary failures.

Use SNS when the primary requirement is broadcasting or notifying multiple subscribers. Use SQS when the primary requirement is storing tasks and allowing workers to process them asynchronously. Use SNS together with multiple SQS queues when the same event must reach several independent applications reliably.
