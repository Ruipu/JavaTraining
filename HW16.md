### Singleton Pattern

**One-line definition:**

Ensures that a class has only one instance throughout the entire application, and provides a global point of access to it.

**Key characteristics:**

- Only one object is ever created — everyone in the system shares that same instance
- A global access point is provided so any part of the system can reach it
- The class controls its own instantiation, so nothing outside can simply create a new one

**Why do we need it:**

- Some resources are expensive to create (e.g. database connections) — recreating them repeatedly wastes resources
- Some things must be globally consistent (e.g. configuration settings, loggers) — having multiple instances would cause conflicts or inconsistency

**Real-life analogy:**

A company has only one CEO. No matter which department needs to contact the CEO, they are always reaching out to the same person.

---

### Factory Pattern

**One-line definition:**

Defines an interface for creating objects, but lets a factory method or subclass decide which class to instantiate — the caller doesn't need to know how the object is created.

**Key characteristics:**

- Separates the "object creation" logic from the business logic
- The caller simply says "I need this type," and the factory returns the right object
- When a new type needs to be added, you only change the factory — not the caller's code

**Why do we need it:**

- When a system needs to create multiple different types of objects based on conditions
- Avoids cluttering the calling code with large `if/else` blocks just to decide which class to instantiate
- Makes the codebase easier to extend and maintain

**Real-life analogy:**

Ordering at Subway — you just say "I want a chicken sandwich." The staff (the factory) handles how it's made. You don't need to know how to bake the bread or slice the meat.

---

### Builder Pattern

**One-line definition:**

Breaks down the construction of a complex object into multiple steps, allowing you to set attributes one at a time and produce the final object at the end.

**Key characteristics:**

- Separates the "building process" from the "final product"
- Each step sets one attribute, and supports method chaining: `setA().setB().setC().build()`
- You can flexibly choose which attributes to set and skip the ones you don't need

**Why do we need it:**

- When an object has many fields, especially optional ones
- Avoids constructors with dozens of parameters that are hard to remember and easy to mix up
- Makes the construction process more readable, flexible, and less error-prone

**Difference from Factory:**

- Factory focuses on **which type** of object to create
- Builder focuses on **how to assemble** a complex object step by step

**Real-life analogy:**

Configuring a new car — you choose the color, then the engine, then the interior, then the wheels, and finally confirm the order. You only pick what matters to you, and end up with a fully customized car.

---

### Proxy Pattern

**One-line definition:**

Provides a substitute or placeholder for a real object — all access to the real object goes through the proxy first, which can perform additional logic before or after forwarding the request.

**Key characteristics:**

- The proxy implements the same interface as the real object, so it looks identical to the caller
- The proxy can insert extra logic around the request: access control, caching, logging, rate limiting, etc.
- You can add new functionality without touching or modifying the original object

**Why do we need it:**

- When you need to control or restrict access to an object
- When you want to add features like logging or caching without changing the original code
- When the real object is expensive to create and you want to delay its initialization

**Real-life analogy:**

A celebrity's agent is a Proxy. If you want to reach the celebrity (the real object), you go through the agent (the proxy) first. The agent checks who you are and what you want, decides whether to pass the message along, and keeps a record of the interaction — all without the celebrity being involved directly.12 Use Cases — Interview Answers

### 12 User Cases

## Singleton Pattern

### 1. Banking — Database Connection Pool Manager

- Banks run thousands of transactions simultaneously across multiple services
- A Singleton manages a shared pool of database connections, so the system reuses existing connections rather than creating a new one for every transaction
- This prevents the database from being overwhelmed, reduces latency, and ensures all services are working from the same connection configuration
- Without it, each service spinning up its own connections could exhaust database resources and cause system-wide failures

### 2. E-Commerce — Logging Service

- An e-commerce platform needs to track every user action — searches, clicks, cart updates, purchases — across the entire application
- A Singleton logging service ensures all modules write to the same log, in the same format, to the same destination
- This makes debugging, auditing, and performance monitoring consistent and reliable
- If multiple logger instances existed, logs could conflict, duplicate, or write to different places, making it nearly impossible to trace issues

### 3. Health Insurance — Configuration Manager

- A health insurance system relies on critical settings such as premium rates, coverage rules, and regulatory thresholds that must be consistent across all services
- A Singleton Configuration Manager loads these settings once at startup and serves as the single source of truth for the entire application
- This ensures every module — claims processing, billing, eligibility checks — operates on the same rules at all times
- It also makes updates easier: changing one config in one place immediately reflects across the whole system

## Factory Pattern

### 4. Banking — Bank Account Creation

- A bank offers multiple account types: Savings, Checking, Fixed Deposit, and Investment accounts — each with different rules, interest logic, and features
- When a customer applies for an account, the system passes the account type to an Account Factory, which creates and returns the correct account object
- The business logic layer doesn't need to know the internal differences between account types — it just asks the factory for what it needs
- This makes it easy to add new account types in the future without changing existing code

### 5. E-Commerce — Payment Processor

- An e-commerce platform supports multiple payment methods: Credit Card, PayPal, Apple Pay, Cryptocurrency, and Buy Now Pay Later
- When a customer checks out, the system passes their selected payment method to a Payment Factory, which instantiates the correct payment processor
- Each processor handles authentication, fees, and confirmation differently — the factory hides all of that complexity from the checkout flow
- Adding a new payment method only requires creating a new class and registering it in the factory — no changes needed elsewhere

### 6. Health Insurance — Insurance Plan Generator

- Health insurers offer different plan types — HMO, PPO, EPO, and POS — each with different networks, referral rules, and cost structures
- When a customer selects a plan, a Plan Factory creates the correct plan object with the appropriate rules and pricing logic
- This keeps the enrollment system clean and decoupled from the complexity of each plan type
- It also makes compliance easier — when regulations change for a specific plan type, only that class needs to be updated

## Builder Pattern

### 7. Banking — Loan Application

- A loan application involves many fields: loan amount, term length, interest rate type (fixed or variable), collateral details, applicant credit history, and repayment schedule
- Many of these fields are optional or depend on the loan type — a personal loan has different requirements than a mortgage
- A Loan Builder allows the system to construct the application step by step, only setting the fields that are relevant to that specific loan type
- This avoids having a single constructor with dozens of parameters, making the code far more readable, maintainable, and less error-prone

### 8. E-Commerce — Order Object

- A customer order can be highly complex: multiple products, quantities, applied discount codes, loyalty points, shipping address, delivery speed, gift wrapping, and payment method
- A Builder constructs the order object step by step as the customer moves through the checkout flow
- Each step adds one piece of information, and the final `build()` call produces a complete, validated order ready to be processed
- This approach also makes it easy to support different order flows — guest checkout, subscription orders, or corporate bulk orders — each using the same builder with different steps

### 9. Health Insurance — Claims Submission

- A medical claim involves patient details, provider information, diagnosis codes, treatment records, itemized costs, supporting documents, and doctor signatures
- Not every claim requires every field — a routine checkup claim looks very different from a surgical procedure claim
- A Claims Builder lets the system assemble only the required fields for each claim type, step by step, before submitting
- This reduces errors in claim submissions, improves compliance with insurance regulations, and makes the system easier to audit

## Proxy Pattern

### 10. Banking — Transaction Authorization

- Every financial transaction — transfers, withdrawals, payments — must pass through security checks before being executed
- A Transaction Proxy sits in front of the real transaction service and performs fraud detection, spending limit validation, and multi-factor authentication before forwarding the request
- If any check fails, the proxy blocks the transaction and raises an alert — the real transaction service is never touched
- This keeps security logic completely separate from transaction logic, making both easier to maintain and audit independently

### 11. E-Commerce — Product Catalog Caching

- An e-commerce site may have millions of product listings being viewed by thousands of users simultaneously
- A Caching Proxy sits in front of the real product database — when a product is requested, the proxy checks its cache first and returns the stored result if available
- Only when the cache is empty or expired does the proxy fetch data from the actual database, then stores it for future requests
- This dramatically reduces database load, speeds up page load times, and improves the overall user experience — especially during high-traffic events like sales

### 12. Health Insurance — Patient Data Access Control

- Patient medical records are highly sensitive and governed by strict privacy regulations such as HIPAA in the US
- A Patient Data Proxy controls all access to the real medical records system — before any record is returned, the proxy verifies the requester's identity, role, and whether they have a legitimate reason to access that specific patient's data
- Doctors can access their own patients' records; administrators have limited access; unauthorized roles are completely blocked
- All access attempts — successful or denied — are logged by the proxy for compliance and audit purposes, without any changes needed to the underlying records system

### What is Microservice Architecture?

Microservice architecture is a software design approach where an application is broken down into a collection of small, independent services, each responsible for one specific business function.

- Each service runs its own process, has its own database, and communicates with other services through APIs or messaging
- Services are loosely coupled — meaning they can be built, deployed, and scaled independently without affecting each other
- Each service is owned by a small team and can be written in different programming languages or use different technologies
- Together, all the services work as one complete application — but behind the scenes, they are completely separate

**Real-world analogy:**

Think of a shopping mall. Each store (service) operates independently — they have their own staff, inventory, and cash register. But together they form one complete shopping experience. If one store closes, the rest of the mall keeps running.

---

### Why Microservice Architecture?

The main reason teams move to microservices is because the alternative — a **Monolithic architecture** — becomes difficult to manage as an application grows.

**Problems with Monolithic architecture that microservices solve:**

- **Scaling bottleneck** — In a monolith, if your payment service is under heavy load, you have to scale the entire application, even parts that don't need it. With microservices, you scale only the payment service independently
- **Deployment risk** — In a monolith, changing one small feature requires redeploying the entire application, which is risky and slow. With microservices, each service deploys independently — a bug in one service doesn't take down the whole system
- **Team independence** — In a monolith, multiple teams working on the same codebase constantly conflict with each other. With microservices, each team owns their own service and can work, test, and release without waiting on others
- **Technology flexibility** — A monolith forces the entire team to use one language and one framework. Microservices allow each service to use the best tool for its specific job
- **Fault isolation** — If one service crashes in a microservice architecture, the rest of the system continues to function. In a monolith, one failure can bring down everything

**In short — microservices are chosen for:**

- Faster development and deployment
- Better scalability
- Higher resilience and fault tolerance
- Larger teams working in parallel without stepping on each other

### Microservice Main Components

A microservice architecture is made up of several key components that work together to keep the system running smoothly:

### API Gateway

- The single entry point for all client requests coming into the system
- Routes each request to the correct microservice
- Handles cross-cutting concerns like authentication, rate limiting, and SSL termination
- Clients never talk directly to individual services — everything goes through the gateway
- Example: AWS API Gateway, Kong, Nginx

### Individual Microservices

- Each service handles one specific business domain — for example: User Service, Order Service, Payment Service, Inventory Service
- Each service has its own codebase and is deployed independently
- Each service exposes its functionality through a well-defined API

### Service-to-Service Communication

- Services need to talk to each other, which happens in two ways:
- **Synchronous** — one service calls another and waits for a response, typically via REST API or gRPC
- **Asynchronous** — one service sends a message and doesn't wait, typically via a message broker like Kafka or RabbitMQ. This is better for performance and resilience

### Message Broker

- Enables asynchronous communication between services
- When one service publishes an event (e.g. "Order Placed"), other services (e.g. Payment, Inventory, Notification) consume that event independently
- Decouples services so they don't need to know about each other directly
- Example: Apache Kafka, RabbitMQ, AWS SQS

### Service Discovery

- In a microservice environment, services are constantly starting up, shutting down, and moving around
- Service Discovery allows services to automatically find and communicate with each other without hardcoded addresses
- Example: Consul, Eureka, Kubernetes built-in DNS

### Load Balancer

- Distributes incoming traffic evenly across multiple instances of the same service
- Prevents any single instance from being overwhelmed
- Improves availability — if one instance goes down, traffic is automatically redirected to healthy ones

### Centralized Logging & Monitoring

- Since requests flow across many services, you need a centralized place to collect and search logs
- Helps trace a single request across multiple services end-to-end (this is called **distributed tracing**)
- Example: ELK Stack (Elasticsearch, Logstash, Kibana), Datadog, Jaeger

### Database per Service

- Each microservice owns its own database — no sharing databases between services
- This ensures services are truly independent and one service's data changes don't break another
- Services can use different types of databases best suited to their needs (SQL, NoSQL, graph, etc.)

### CI/CD Pipeline

- Each microservice has its own automated pipeline for building, testing, and deploying
- A change to one service triggers only that service's pipeline, not the entire system
- This enables teams to release updates multiple times per day safely

### Config Server

A Config Server is a centralized place to store and manage configuration properties (like database URLs, API keys, port numbers) for all your microservices — instead of hardcoding configs inside each service.

**Why do we need it?**

- In a microservice system, you might have 20+ services, each needing their own config
- Without a config server, changing one setting (e.g. database URL) means updating and redeploying every single service
- With a config server, you change it in one place and all services pick it up automatically

**How it works:**

- You store all config files in a **Git repository**
- The Config Server connects to that Git repo and serves the configs
- Each microservice fetches its own config from the Config Server on startup
- If config changes, services can refresh without restarting

```
# Config Server — application.yml
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/your-org/config-repo

# Each Microservice — bootstrap.yml
spring:
  application:
    name: payment-service
  config:
    import: configserver:http://localhost:8888
```

**Key concepts:**

- `@EnableConfigServer` — marks a Spring Boot app as the Config Server
- Each service calls `http://config-server/service-name/profile` to get its config
- Supports **environment profiles**: dev, staging, production configs all in one place
- Supports **encryption** of sensitive values like passwords

### Service Discovery — Eureka, Consul, Zookeeper

**What is it?**

Service Discovery is a mechanism that allows microservices to automatically find and communicate with each other — without hardcoding IP addresses or ports.

**Why do we need it?**

- In a dynamic cloud environment, services constantly start, stop, and move
- You can't hardcode `http://192.168.1.5:8080` because that IP might change at any time
- Service Discovery keeps a live registry of all running services and their current locations

**How it works:**

- Each service **registers** itself with the Discovery Server when it starts up
- When Service A wants to talk to Service B, it **queries** the Discovery Server for Service B's current address
- The Discovery Server constantly checks which services are still alive (heartbeat)

```
# Eureka Server — application.yml
eureka:
  client:
    register-with-eureka: false
    fetch-registry: false

# Each Microservice — application.yml
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
spring:
  application:
    name: order-service   # This is how other services find you
```

**Eureka vs Consul vs Zookeeper:**

| Tool | Best For | Key Feature |
| --- | --- | --- |
| **Eureka** | Spring Boot / Netflix stack | Simple, built for microservices, AP (available) |
| **Consul** | Multi-language systems | Also does health checks, KV store, service mesh |
| **Zookeeper** | High consistency needs | CP (consistent), used heavily in Kafka/Hadoop |

**Key concepts:**

- **Service Registry** — the database of all registered services
- **Heartbeat** — services ping the registry every 30s to say "I'm still alive"
- **Self-preservation mode** (Eureka) — if many services go offline at once, Eureka assumes a network issue and doesn't remove them all

### 3. Zipkin & Sleuth — Distributed Tracing

**What is it?**

- **Spring Cloud Sleuth** — automatically adds a unique trace ID to every request as it travels across microservices
- **Zipkin** — collects all those trace IDs and gives you a visual UI to see the full journey of a request

**Why do we need it?**

- A single user request might touch 5 different services: Gateway → Order → Payment → Inventory → Notification
- If something goes wrong or is slow, how do you know which service is the culprit?
- Sleuth tags every log with the same trace ID, and Zipkin draws the full timeline so you can see exactly where time was spent or where errors occurred

```
# Every log automatically gets tagged:
[order-service, traceId=abc123, spanId=def456] Processing order...
[payment-service, traceId=abc123, spanId=ghi789] Charging card...
[inventory-service, traceId=abc123, spanId=jkl012] Updating stock...

# Same traceId = same original request
# Different spanId = different service handling it
```

**Key concepts:**

- **Trace** — the entire journey of one request across all services
- **Span** — one single operation within that journey (e.g. the time spent in Payment Service)
- **TraceId** — unique ID shared across all services for one request
- **SpanId** — unique ID for each individual service's portion of the work
- Zipkin UI lets you click on any trace and see a waterfall timeline showing how long each service took

---

**Dependencies**

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-sleuth</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-sleuth-zipkin</artifactId>
</dependency>
```

**Note:** Spring Cloud Sleuth has been deprecated and migrated into **Micrometer Tracing** in newer Spring Boot 3.x projects — but the concept is identical.

### Ribbon — Client-Side Load Balancer

**What is it?**

Ribbon is a **client-side load balancer** — instead of a central load balancer deciding where to send traffic, each service client decides for itself which instance to call.

**Why do we need it?**

- In a microservice system, you might have 3 instances of the Payment Service running
- Ribbon automatically distributes requests across all 3 instances
- If one instance is down, Ribbon skips it and picks a healthy one

**Client-side vs Server-side Load Balancing:**

|  | Server-Side (e.g. Nginx) | Client-Side (Ribbon) |
| --- | --- | --- |
| **Who decides?** | A central load balancer server | The calling service itself |
| **How?** | All traffic goes to one entry point, which then routes | Client fetches the list of instances from Eureka and picks one |
| **Advantage** | Simple, central control | No single point of failure, faster |

**How it works:**

- Ribbon integrates with Eureka to get the list of available instances for a service
- When your service wants to call `order-service`, Ribbon picks one of the available instances using a load balancing algorithm
- Default algorithm: **Round Robin** (cycles through instances one by one)
- Other algorithms: Random, Weighted Response Time, Availability Filtering

```yaml
# application.yml — customize Ribbon behavior
order-service:
  ribbon:
    NFLoadBalancerRuleClassName: com.netflix.loadbalancer.RandomRule
```

**Note:** Ribbon is now in **maintenance mode**. Spring Cloud has replaced it with **Spring Cloud LoadBalancer**, but the concept remains the same and Ribbon is still widely seen in legacy systems and interview questions.

### ELK Stack — Elasticsearch, Logstash, Kibana

**What is it?**

ELK is a three-tool stack for centralized log collection, storage, and visualization across all your microservices.

**Why do we need it?**

- With 20 microservices each writing their own logs to their own files, finding the cause of an error is nearly impossible
- ELK collects all logs into one place, makes them searchable, and lets you build visual dashboards

**The three components:**

### Elasticsearch

- A powerful **search and storage engine** for logs
- Stores logs as JSON documents
- Lets you search through millions of log entries in milliseconds
- Think of it as Google Search, but for your logs

### Logstash

- A **data pipeline** that collects, transforms, and forwards logs
- Can receive logs from many sources (files, Kafka, syslog, etc.)
- Can filter, parse, and enrich logs before sending them to Elasticsearch
- Example: parsing a raw log line and extracting the timestamp, log level, and service name into structured fields

### Kibana

- The **visual dashboard** on top of Elasticsearch
- Lets you search and filter logs in a web UI
- Build charts and dashboards: error rates over time, request counts per service, slowest endpoints
- Set up alerts when error rates spike

**How they work together:**

```
Microservice logs
      ↓
  Logstash        ← collects and transforms logs
      ↓
Elasticsearch     ← stores and indexes logs
      ↓
  Kibana          ← search, visualize, and alert
```

**Common pattern in Spring Boot:**

- Add a **Logback** appender that sends logs to Logstash
- Logstash processes and forwards to Elasticsearch
- Team uses Kibana to monitor and debug production issues in real time

### Circuit Breaker — Fallback

**What is it?**

A Circuit Breaker is a pattern that **stops calling a failing service** and immediately returns a fallback response — instead of letting the failure cascade through your entire system.

**Why do we need it?**

- In a microservice chain, if Service C is slow or down, Service B waiting for it gets stuck, and then Service A waiting for B gets stuck too
- This cascading failure can bring down your entire system
- A Circuit Breaker detects the failure early and "opens the circuit" — just like an electrical circuit breaker cutting the power to prevent damage

**Three states of a Circuit Breaker:**

```
CLOSED ──(failures exceed threshold)──► OPEN ──(wait timeout)──► HALF-OPEN
  ▲                                                                    │
  └──────────────(test call succeeds)─────────────────────────────────┘
```

- **Closed** — everything is normal, requests go through
- **Open** — too many failures detected, circuit is open, all requests immediately return fallback (no waiting)
- **Half-Open** — after a timeout, lets a few test requests through to see if the service recovered

**Fallback example concept:**

Normal:   User Request → Payment Service → Bank API ✅
Failure:  Bank API is down
Without Circuit Breaker: request hangs for 30s then times out ❌
With Circuit Breaker:    immediately returns "Payment temporarily unavailable, please try again later" ✅

### Hystrix → Resilience4j

### Hystrix (Legacy — Netflix, now deprecated)

- The original Circuit Breaker library by Netflix
- Widely used in Spring Cloud Netflix stack
- Still seen in many legacy codebases and interview questions
- **Now in maintenance mode** — Netflix stopped active development

### Resilience4j (Modern replacement)

- The current standard Circuit Breaker for Spring Boot applications
- Lightweight, modular, and designed specifically for Java 8+ and functional programming
- Provides more than just Circuit Breaker:

**Resilience4j modules:**

| Module | What it does |
| --- | --- |
| **CircuitBreaker** | Stops calls to failing services, opens the circuit |
| **Retry** | Automatically retries a failed request N times before giving up |
| **RateLimiter** | Limits how many requests can be made per second |
| **Bulkhead** | Limits concurrent calls to a service to prevent overload |
| **TimeLimiter** | Sets a timeout — if no response in X seconds, fail fast |

**How to use Resilience4j:**

```java
// Annotate your method — that's it
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public String processPayment(Order order) {
    return paymentServiceClient.charge(order);
}

// Fallback method — called when circuit is open
public String paymentFallback(Order order, Exception e) {
    return "Payment service is temporarily unavailable. Please try again later.";
}
```

```yaml
# application.yml — configure the circuit breaker
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        failure-rate-threshold: 50        # Open circuit if 50% of calls fail
        wait-duration-in-open-state: 10s  # Stay open for 10 seconds
        sliding-window-size: 10           # Look at last 10 calls to decide
```
