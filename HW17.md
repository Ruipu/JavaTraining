### **What is Docker, Dockerfile, Docker image, and Docker container?**

**Docker is a containerization platform.** 

It is used to package an application together with the runtime environment it needs, so the application can run consistently across different machines and environments. 

For example, if I have a Spring Boot application that requires Java 17, Docker allows me to package the application, the Java runtime, and the startup command into a standard containerized unit. This helps avoid the common problem where the application works on one developer’s machine but fails in QA or production because the environment is different.

**A Dockerfile is the instruction file used to build a Docker image.** 

It defines what base environment the application needs, what files should be copied into the image, what dependencies are required, which port should be exposed, and what command should run when the container starts. 

In a Spring Boot project, the Dockerfile usually describes how to take the built jar file and run it with a Java runtime. So the Dockerfile itself is not the running application. It is more like a recipe for creating the application image.

**A Docker image is the packaged, read-only template created from the Dockerfile.** 

It contains the application code or artifact, the runtime environment, and the instructions needed to start the application. 

For example, after building a Spring Boot project, we can create an image that includes the jar file and Java 17. The image itself is static. It is not running yet. It can be stored in a container registry such as Docker Hub, AWS ECR, or a company’s private registry.

**A Docker container is a running instance of a Docker image.** 

If the image is like a class, then the container is like an object created from that class. The same image can be used to start multiple containers. 

Each container runs in an isolated environment with its own process, filesystem, network configuration, and runtime state. In simple terms, the Dockerfile builds the image, the image is the packaged application template, and the container is the actual running application.

### **Docker vs VM**

**Docker and virtual machines are both used for environment isolation, but they work at different levels.** 

**A virtual machine** virtualizes an entire operating system. Each VM usually has its own guest operating system, kernel, libraries, and application runtime. Because of that, VMs provide strong isolation, but they are also heavier, slower to start, and consume more CPU, memory, and disk resources.

**Docker containers** are more lightweight because they share the host operating system kernel. A container only packages the application and the user-space dependencies needed to run it. It does not need to start a full guest operating system. Because of this, containers usually start much faster and use fewer resources than virtual machines. This makes Docker very suitable for microservices, CI/CD pipelines, and cloud deployment.

***The simple difference is that a VM virtualizes a whole machine, while Docker containerizes an application environment.*** 

***VMs are useful when we need full operating system isolation. Docker is useful when we want to package, ship, and run applications quickly and consistently.***

### **How to use Docker in a real project**

**In a real project, Docker is usually used in both local development and deployment.** 

During local development, developers may still write and debug Spring Boot code in IntelliJ, but they can use Docker to run external dependencies such as Postgres, Redis, Kafka, RabbitMQ, or MongoDB. 

This avoids the need to manually install all those services on the local machine. For example, my Spring Boot application can run in IntelliJ, while the Postgres database runs inside a Docker container. This makes the local environment easier to set up and more consistent across the team.

**After the application is developed, Docker is used as part of the build and deployment process.**

Developers write code, push a branch, and create a pull request. After the PR is approved and merged, the CI/CD pipeline can build the Spring Boot application, run tests, create a jar file, build a Docker image from the Dockerfile, and push that image to a container registry. Then the deployment system can pull the same image and run it in QA, UAT, staging, or production.

**In a real company, the Docker image often becomes the standard deployment artifact.** 

Instead of manually copying jar files to servers and installing Java on each server, the team builds one image and deploys that image across environments. 

A good practice is “build once, deploy many times.” That means the same Docker image can be tested in QA and later promoted to production. The application image stays the same, while environment-specific configurations, such as database URLs, credentials, active Spring profiles, and API keys, are injected through environment variables, config servers, Kubernetes ConfigMaps, or secrets.

**In a microservices project, each service can have its own Docker image.** 

For example, an employee service, department service, API gateway, discovery service, and config server can all be containerized separately. In local development, Docker Compose can be used to start multiple services together. 

In production, containers are often managed by Kubernetes, AWS ECS, or another orchestration platform. This makes Docker very useful for standardizing environments, simplifying deployment, and supporting scalable microservice architecture.

## **General AWS Console Entry Point**

First, log in to the AWS Management Console. In most cases, the easiest way to find a service is to use the search bar at the top-left of the console. You can directly search for service names such as `EC2`, `ECS`, `ECR`, `RDS`, `DynamoDB`, `Lambda`, or `API Gateway`.

Before checking any service, always look at the **Region** in the top-right corner of the AWS Console. Many AWS resources are region-specific. For example, an EC2 instance or RDS database created in `us-east-1` may not appear if you switch to `us-east-2`.

Also, be careful with buttons such as **Create**, **Launch**, **Deploy**, or **Start**. Many AWS services may generate costs once resources are created. If the task is only to check and understand the service, you usually do not need to finish the creation process.

## **EC2**

EC2 stands for Elastic Compute Cloud. It provides virtual servers in the AWS Cloud. In a real project, EC2 can be used to deploy backend applications, run Docker containers, host internal services, install Nginx, or run a Spring Boot jar file directly on a cloud server.

To check EC2 in the AWS Console, use the search bar and type `EC2`. Click **EC2**. On the left-side menu, click **Instances**. This page shows all EC2 instances in the selected region. 

You should check the instance ID, instance name, instance state, instance type, public IPv4 address, private IPv4 address, and security group.

**If you want to inspect one instance, click the instance ID. At the bottom of the page, you will see tabs such as Details, Security, Networking, Storage, Status checks, and Monitoring.**

In the **Details** tab, check the instance type, AMI, public IP, private IP, and key information about the server. In the **Security** tab, check the security group. The security group controls which ports are open. For example, port 22 is used for SSH, port 8080 may be used for a Spring Boot application, and ports 80 and 443 are used for HTTP and HTTPS. In the **Networking** tab, check the VPC, subnet, and IP addresses. In the **Storage** tab, check the EBS volume attached to the instance. In the **Monitoring** tab, you can check CPU usage, network traffic, and other instance metrics.

**If you only want to see how to create an EC2 instance, go to Instances and click Launch instances**. 

You will need to enter a name, choose an AMI such as Amazon Linux, select an instance type, choose or create a key pair, configure network settings, select a VPC and subnet, configure the security group, and configure storage. You do not need to complete the launch unless you are sure you want to create the instance.

**In a real project, EC2 can be used as the server layer.** 

For example, a team can deploy a Spring Boot application to EC2 by installing Java and running the jar file. Another common approach is to install Docker on EC2 and run application containers there. However, in many modern projects, teams often use ECS, EKS, or Kubernetes instead of manually deploying applications on EC2.

## **ECR**

**ECR stands for Elastic Container Registry. It is AWS’s managed container image registry.** 

You can think of it as the AWS version of Docker Hub. After a Spring Boot application is packaged into a Docker image, the image can be pushed to ECR. Then ECS, EKS, or another deployment platform can pull the image from ECR and run it.

**To check ECR in the AWS Console, search for `ECR` and click Elastic Container Registry.** 

**On the left-side menu, click Repositories. This page shows all container image repositories in the selected region. Click a repository name to inspect it.**

Inside a repository, you can check the image tags, image URI, pushed time, image size, and scan results. The repository URI is very important because ECS task definitions or deployment pipelines use this URI to locate the image. You should also check lifecycle policies, which control how old images are cleaned up, and permissions, which control who can push and pull images.

**If you only want to see how to create an ECR repository, go to Repositories and click Create repository.** 

Usually, you choose **Private** visibility. Then you enter a repository name such as `employee-service`. You can also check settings such as image tag mutability, scan on push, and encryption. You do not need to actually create it unless required.

In a real project, ECR is usually used in the CI/CD pipeline. After a pull request is approved and merged, the pipeline builds the Spring Boot application, creates a Docker image, tags the image, and pushes it to ECR. Later, ECS or another runtime environment pulls the same image from ECR and runs it as a container.

## **ECS**

**ECS stands for Elastic Container Service. It is used to run and manage containers on AWS. If ECR stores Docker images, ECS runs those images as containers.**

There are several important ECS concepts. 

A **Cluster** is the logical environment where containers run. 

A **Task Definition** describes how a container should run, including the image URI, CPU, memory, port mapping, environment variables, and IAM roles. 

A **Task** is a running instance of a task definition. 

A **Service** keeps tasks running over time and maintains the desired number of running containers. For example, a service can be configured to always keep two tasks running. ECS can run containers using **Fargate**, where AWS manages the infrastructure, or using the **EC2 launch type**, where containers run on EC2 instances managed by the team.

To check ECS in the AWS Console, search for `ECS` and click **Elastic Container Service**. 

On the left-side menu, click **Clusters**. Click a cluster name. Inside a cluster, check **Services**, **Tasks**, **Infrastructure**, and **Metrics**.

If there is an ECS service, click the service name. Inside the service page, check **Deployments**, **Tasks**, **Configuration**, **Networking**, and **Events**. The **Events** section is very useful when deployment fails because it often shows why tasks cannot start.

**You should also check Task definitions from the left-side menu.** 

Click a task definition and inspect the container image URI, CPU and memory settings, port mappings, environment variables, task role, and task execution role. The image URI usually points to an ECR image.

If you only want to see how to create an ECS cluster, go to **Clusters** and click **Create cluster**. Enter a cluster name. For many learning or modern deployment scenarios, choose AWS Fargate because you do not need to manage EC2 instances. You can review the configuration without actually creating the cluster.

**If you want to inspect how a task definition is created, go to Task definitions and click Create new task definition.** 

You will enter a task definition family name, choose a launch type such as Fargate, configure container details, paste the ECR image URI, set the container port such as 8080, configure CPU and memory, add environment variables, and choose IAM roles.

In a real project, ECS is commonly used to deploy Spring Boot microservices. For example, `employee-service` is built into a Docker image and pushed to ECR. Then an ECS service uses a task definition to pull that image and run the container. A load balancer or API Gateway can route external requests to the ECS service.

## **RDS**

**RDS stands for Relational Database Service.** 

It is AWS’s managed relational database service. It supports database engines such as PostgreSQL, MySQL, MariaDB, Oracle, and SQL Server. For a Spring Boot project, RDS is commonly used as the main relational database.

**To check RDS in the AWS Console, search for `RDS` and click RDS.** 

On the left-side menu, click **Databases**. This page shows existing DB instances and clusters. Click a database name to inspect it.

**Inside the database page, check Connectivity & security, Monitoring, Configuration, Logs & events, and Maintenance & backups.** 

In **Connectivity & security**, you should check the endpoint, port, VPC, subnet group, security group, and public accessibility. The endpoint and port are used by your Spring Boot application to connect to the database. For example, PostgreSQL usually uses port 5432, and MySQL usually uses port 3306.

In the **Configuration** section, check the database engine, engine version, DB instance class, storage, backup setting, and maintenance window. In a real production environment, public access is usually disabled, and the database is only reachable from services inside the same VPC or allowed security groups.

**If you only want to see how to create an RDS database, go to Databases and click Create database.** 

Choose **Standard create**. Select an engine type such as PostgreSQL or MySQL. Choose a template such as Dev/Test or Free tier if you are only learning. Enter the DB instance identifier, master username, and password. Then configure the instance class, storage, VPC, subnet group, public access, and security group. You can also set the initial database name in additional configuration. Do not actually create it unless you are sure because RDS can easily generate costs.

In a real project, RDS stores structured business data. For example, in an Employee Management System, entities such as employees, departments, users, roles, orders, and transactions can be stored in RDS. A Spring Boot application can connect to RDS through JDBC, JPA, Hibernate, or Spring Data JPA.

## **DocumentDB**

DocumentDB is AWS’s managed document database service that is compatible with MongoDB workloads. **It is used to store JSON-like document data. It is different from RDS because it is not a relational database.**

To check DocumentDB in the AWS Console, search for `DocumentDB` and click **Amazon DocumentDB**. 

On the left-side menu, click **Clusters**. This page shows existing DocumentDB clusters. Click a cluster name to inspect it.

Inside the cluster page, check **Connectivity & security**, **Configuration**, **Instances**, **Monitoring**, and **Events**. You should check the cluster endpoint, reader endpoint, port, VPC, subnet group, and security group. The default port is usually 27017. The cluster endpoint is used by the application to connect to DocumentDB.

**You should also check the instances inside the cluster, including the primary instance and replicas.** 

In **Configuration**, check the engine version, backup setting, maintenance window, and storage-related settings.

If you only want to see how to create a DocumentDB cluster, go to **Clusters** and click **Create**. Enter a cluster identifier, username, password, instance class, VPC, subnet group, and security group. Do not create it unless necessary because DocumentDB is usually not cheap.

In a real project, DocumentDB is useful when the application needs to store flexible JSON-like data. Examples include user profile preferences, product catalog metadata, semi-structured application data, activity documents, and some types of logs. A Spring Boot application can connect to DocumentDB using MongoDB-compatible drivers or Spring Data MongoDB.

## **DynamoDB**

DynamoDB is AWS’s fully managed NoSQL key-value and document database. 

It is designed for high scalability and low-latency access. It is commonly used for data that can be queried by key, such as session data, shopping carts, user preferences, idempotency records, feature flags, event state, and high-throughput application metadata.

**To check DynamoDB in the AWS Console, search for `DynamoDB` and click DynamoDB.** 

On the left-side menu, click **Tables**. This page shows existing DynamoDB tables. Click a table name to inspect it.

Inside a table, check **Overview**, **Indexes**, **Monitor**, **Global tables**, **Backups**, **Exports and streams**, and **Additional settings**. To view actual data, click **Explore table items**.

**The most important thing to check is the table key design.** 

Check the **Partition key** and, if available, the **Sort key**. The partition key determines how data is distributed and queried. You should also check **Indexes**, especially Global Secondary Indexes, because they allow additional query patterns. Check the capacity mode, which can be on-demand or provisioned. Also check whether Streams and TTL are enabled.

**If you only want to see how to create a table, go to Tables and click Create table. Enter the table name, partition key, and optional sort key. You can review the default table settings without actually creating** it.

In a real project, DynamoDB is often used together with relational databases. For example, core business data can be stored in RDS, while audit records, session state, user preferences, or high-speed event state can be stored in DynamoDB. DynamoDB is especially useful when the access pattern is clear and mostly based on primary key or indexed queries.

## **Lambda Function**

**Lambda is AWS’s serverless compute service.** 

It allows developers to run code without managing servers. Instead of starting an EC2 instance or running a long-lived container, you create a function and AWS runs it when it is triggered.

**To check Lambda in the AWS Console, search for `Lambda` and click Lambda.** 

On the left-side menu, click **Functions**. This page shows existing Lambda functions. Click a function name to inspect it.

Inside a Lambda function, check **Code**, **Test**, **Configuration**, **Monitor**, **Aliases**, and **Versions**. In **Code**, you can view or edit the function code depending on the runtime and deployment method. In **Configuration**, check the runtime, handler, memory, timeout, environment variables, triggers, and permissions.

**The Permissions section is very important because it shows the Lambda execution role.** 

This role controls what the Lambda function is allowed to access. For example, if a Lambda function needs to read from DynamoDB or send messages to SQS, its execution role must have those permissions.

**The Triggers section shows what invokes the function.** 

A Lambda function can be triggered by API Gateway, SQS, SNS, Kinesis, S3, EventBridge, DynamoDB Streams, and other AWS services. In **Monitor**, you can check metrics and logs. Most runtime errors can be found in CloudWatch Logs.

If you only want to see how to create a Lambda function, go to **Functions** and click **Create function**. 

Choose **Author from scratch**, enter a function name, select a runtime such as Java, Python, or Node.js, and choose an execution role. You can review the setup without actually creating the function.

In a real project, Lambda is useful for event-driven tasks. For example, it can send a welcome email after user registration, process an uploaded file after it lands in S3, consume messages from an SQS queue, process streaming events, run scheduled jobs, or provide a lightweight API behind API Gateway. For a large Spring Boot backend, ECS or EC2 may be more appropriate, but Lambda is very useful for small independent tasks and event-driven workflows.

## **API Gateway**

**API Gateway is AWS’s service for creating, publishing, securing, monitoring, and managing APIs.** 

It can expose REST APIs, HTTP APIs, and WebSocket APIs. It can route requests to Lambda functions, HTTP backends, AWS services, or private resources through VPC Link.

To check API Gateway in the AWS Console, search for `API Gateway` and click **API Gateway**. 

On the main page or left-side menu, go to **APIs**. You will see REST APIs, HTTP APIs, and WebSocket APIs. Click an API name to inspect it.

For a REST API, check **Resources**, **Methods**, **Stages**, **Authorizers**, **Gateway Responses**, and **Models**. For an HTTP API, check **Routes**, **Integrations**, **Stages**, **Authorization**, and **CORS**.

**The most important things to check are the API routes, methods, integrations, stages, and invoke URL.** 

A route may be something like `GET /employees` or `POST /orders`. The integration defines where the request goes, such as a Lambda function, ECS service through a load balancer, or another HTTP endpoint. Stages represent environments such as `dev`, `qa`, or `prod`. CORS settings are important if the API is called from a frontend application.

**If you only want to see how to create an API, click Create API.** 

Choose HTTP API or REST API. HTTP API is usually simpler and lighter. REST API provides more advanced features. Then configure the integration, add routes, define a stage, and review the settings. You do not need to actually create it unless required.

In a real project, API Gateway is often the external entry point. A client sends requests to API Gateway. API Gateway handles routing, authorization, CORS, throttling, monitoring, and sometimes request transformation. Then it forwards the request to Lambda, ECS, or another backend service.

## **Kinesis**

**Kinesis is used for real-time streaming data. Kinesis Data Streams can collect and process continuous streams of data records in real time. It is commonly used for clickstream data, logs, IoT events, transaction events, analytics events, and real-time monitoring pipelines.**

To check Kinesis in the AWS Console, search for `Kinesis` and click **Kinesis**. You will usually see services such as Kinesis Data Streams, Data Firehose, and Managed Service for Apache Flink. For basic checking, click **Data Streams**. This page shows existing streams. Click a stream name to inspect it.

**Inside a stream, check Configuration, Monitoring, Data viewer, and Consumers.** 

You should check the stream name, capacity mode, number of shards if it is provisioned, retention period, consumers, and monitoring metrics. Important metrics include incoming records, outgoing records, and iterator age. Iterator age is useful because it shows whether consumers are falling behind.

If you only want to see how to create a Kinesis data stream, go to **Data Streams** and click **Create data stream**. Enter a stream name and choose a capacity mode such as on-demand or provisioned. You can review the configuration without actually creating it.

In a real project, Kinesis is used when the system needs real-time event streaming. For example, an order service can publish order events, and multiple downstream consumers can process those events for analytics, fraud detection, monitoring, or reporting. Compared with SQS, Kinesis is more suitable for streaming data and multiple consumers reading the same stream. SQS is more suitable for queue-based asynchronous task processing.

## **IAM**

**IAM stands for Identity and Access Management. It is the AWS service used to manage users, roles, policies, and permissions. IAM controls who can access which AWS resources and what actions they can perform.**

To check IAM in the AWS Console, search for `IAM` and click **IAM**. 

IAM is a global service, so it is not tied to one specific region in the same way EC2 or RDS is. On the left-side menu, you will see **Users**, **User groups**, **Roles**, **Policies**, and **Identity providers**.

To check a user, click **Users**, then click a username. 

You can inspect the user’s permissions, groups, and security credentials. Be careful with access keys. Do not create or expose access keys unless required.

To check a role, click **Roles**, then click a role name. 

You should check **Permissions** and **Trust relationships**. Permissions define what the role can do. Trust relationships define who can assume the role. For example, a Lambda execution role may trust the Lambda service, and an ECS task role may trust ECS tasks.

To check a policy, click **Policies**, search for the policy name, and open it. 

You can view the policy as JSON or through the visual editor. The important parts are Effect, Action, and Resource. Effect is usually Allow or Deny. Action defines what operations are allowed, such as reading from S3 or writing to DynamoDB. Resource defines which AWS resources the policy applies to.

In a real project, IAM is critical for security. A Lambda function that needs to access DynamoDB must have a Lambda execution role with DynamoDB permissions. An ECS task that needs to pull images from ECR needs an execution role. An EC2 instance that needs to access S3 should use an IAM role instead of hardcoded access keys. A good practice is to follow least privilege, which means each user or service should only have the permissions it actually needs.

## **SNS**

**SNS stands for Simple Notification Service. It is a publish-subscribe messaging service. It allows one publisher to send a message to a topic, and multiple subscribers can receive that message.**

Subscribers can include SQS queues, Lambda functions, email addresses, SMS endpoints, HTTP endpoints, and other supported targets.

To check SNS in the AWS Console, search for `SNS` and click **Simple Notification Service**. 

On the left-side menu, click **Topics**. This page shows existing SNS topics. Click a topic name to inspect it.

Inside a topic, check **Subscriptions**, **Access policy**, **Delivery status logging**, and **Encryption**. 

The **Topic ARN** is important because other services use it to publish messages to the topic. The topic type can be Standard or FIFO. In **Subscriptions**, you can see which endpoints receive messages from the topic.

If you only want to see how to create an SNS topic, go to **Topics** and click **Create topic**. Choose Standard or FIFO, enter a topic name, and review the settings. You do not need to actually create it unless required.

To check subscriptions, go to **Subscriptions** on the left-side menu. Click **Create subscription** to see the setup. You select a Topic ARN, choose a protocol such as SQS, Lambda, Email, or HTTP, and then enter the endpoint.

In a real project, SNS is useful for event broadcasting. For example, when an order is created, the order service can publish an `OrderCreated` event to an SNS topic. Then the email service, inventory service, and analytics service can each subscribe to the same topic and react independently. SNS is useful when one event needs to be delivered to multiple downstream systems.

## **SQS**

**SQS stands for Simple Queue Service.** 

It is a managed message queue service. It allows one service to send messages to a queue and another service to consume those messages asynchronously. This helps decouple services and makes the system more reliable.

To check SQS in the AWS Console, search for `SQS` and click **Simple Queue Service**. On the left-side menu, click **Queues**. This page shows existing queues. Click a queue name to inspect it.

Inside a queue, check **Details**, **Monitoring**, **Dead-letter queue**, **Lambda triggers**, **Access policy**, **Encryption**, and **Send and receive messages**. 

The **Queue URL** is used by applications to send messages. The **ARN** is used in integrations with SNS, Lambda, IAM, and other AWS services.

Important settings include the queue type, visibility timeout, message retention period, delivery delay, receive message wait time, and dead-letter queue. A Standard queue provides high throughput and at-least-once delivery. A FIFO queue provides ordering and exactly-once processing semantics within certain limits.

The visibility timeout controls how long a message is hidden from other consumers after one consumer receives it. If the consumer processes the message successfully, it deletes the message. If the consumer fails and does not delete it, the message becomes visible again after the visibility timeout. A dead-letter queue stores messages that fail processing too many times.

If you only want to see how to create a queue, go to **Queues** and click **Create queue**. Choose Standard or FIFO, enter a queue name, and review settings such as visibility timeout, message retention period, and dead-letter queue. You do not need to actually create it unless required.

In a real project, SQS is commonly used for asynchronous processing. For example, after a user places an order, the order service can send a message to SQS. The email service can consume the message later and send a confirmation email. This prevents the main request from being blocked by slow downstream services. If a downstream service is temporarily unavailable, messages can stay in the queue and be retried later.

SNS and SQS are often used together. SNS is used for broadcasting an event, and SQS is used for reliable queue-based consumption. For example, one SNS topic can fan out messages to multiple SQS queues. Each downstream service can have its own queue and process messages independently.

## **Project-Level Understanding**

In a real Spring Boot microservices project, these AWS services can work together as one architecture.

The client sends a request to API Gateway. API Gateway routes the request to a Spring Boot service running on ECS, or to a Lambda function. The Docker image of the Spring Boot service is stored in ECR. ECS pulls the image from ECR and runs it as a container based on a task definition.

If the project does not use ECS, the Spring Boot application can also be deployed directly on EC2. In that case, EC2 acts as the cloud server where the application runs.

Structured business data, such as employees, users, orders, products, and transactions, can be stored in RDS. Flexible JSON-like document data can be stored in DocumentDB. High-throughput key-value data, session state, user preferences, audit records, or event state can be stored in DynamoDB.

For asynchronous processing, services can use SQS. For event broadcasting, services can use SNS. For real-time streaming data, services can use Kinesis. Lambda functions can be triggered by API Gateway, SQS, SNS, Kinesis, S3, or EventBridge to process events without managing servers.

IAM controls permissions across all of these services. ECS tasks, Lambda functions, EC2 instances, and CI/CD pipelines should use IAM roles and policies instead of hardcoded credentials.

A typical flow could look like this: the frontend calls API Gateway, API Gateway forwards the request to an ECS service, the ECS service reads or writes data in RDS or DynamoDB, then publishes an event to SNS or sends a message to SQS. A Lambda function or another ECS service consumes the event and handles follow-up work. The whole system uses IAM roles to control access between services.
